# Five stdlib native modules with ConstantSymbol infrastructure (v2)

This change adds five Python standard library modules to minipy (math, string, functools, random, sys) plus ConstantSymbol infrastructure for non-callable module attributes. The v1 review's blocking issues have been addressed: dynamic-typed arguments now route to runtime-dispatch host functions that accept `TypeRef` parameters and unbox at runtime, `intBinarySymbol` was removed in favor of direct `NewSymbol` calls, documentation was added for all behavioral deviations, and integration tests now cover the runtime error paths (factorial(-1), reduce empty, randrange empty, choice empty).

Watch for: `randint(a, b)` with `b < a` panics the Go runtime because `Int64N` receives a non-positive argument — no guard exists in either the static or dynamic host function (confirmed). `unboxFloat`, `unboxInt`, and `vmParamType` are copy-pasted identically between `math/math.go` and `random/random.go`, creating a drift hazard as more stdlib modules adopt dynamic dispatch (confirmed). Host function factories (`randomHost()`, `gcdHost()`, etc.) still allocate fresh identical objects per emit call (confirmed, non-blocking).

**Verdict**: NEEDS_CHANGES

## High-level view

The `randint` host function remains unguarded against inverted ranges. `Int64N(n)` in Go's `math/rand/v2` panics when `n <= 0`. If a minipy program calls `randint(5, 3)`, the resulting `Int64N(-1)` brings down the entire Go process rather than producing a user-visible runtime error. This is a correctness bug distinct from the `randrange` guard (which was already fixed).

The helper trio (`unboxFloat`, `unboxInt`, `vmParamType`) is now duplicated verbatim across two packages. When a third module needs dynamic dispatch (e.g., `operator` extensions or a future `statistics` module), this creates three places to update. Extracting to a shared package (perhaps `hostabi` which already exists and provides `ArrayElems`) would centralize the pattern.

## randint panic on inverted range

Both `randintHost()` and `dynRandintHost()` pass `b-a+1` directly to `rng.Int64N`:

```go
// random/random.go line 327
v := a + rng.Int64N(b-a+1)
```

Go's `rand.Rand.Int64N` documents: "Int64N panics if n <= 0." When `b < a`, `b-a+1` is zero or negative. Unlike `randrange` (which guards `stop <= start`), `randint` has no such check. A minipy program like `random.randint(10, 5)` will panic with a Go stack trace rather than a clean `ErrEmptyRange` error propagated through the VM's trap mechanism.

The fix is a three-line guard before the `rng.Int64N` call in both the static and dynamic variants:

```go
if b < a {
    return nil, ErrEmptyRange // or a new ErrInvalidRange
}
```

## Duplicated dynamic-dispatch helpers

The following three functions appear identically in both `math/math.go` and `random/random.go`:

- `unboxFloat(i *interp.Interpreter, v vmtypes.Boxed) (float64, error)` — 20 lines
- `unboxInt(i *interp.Interpreter, v vmtypes.Boxed) (int64, error)` — 16 lines
- `vmParamType(t types.Type) vmtypes.Type` — 6 lines

The `hostabi` package already exists as the shared surface for host function utilities (it exports `ArrayElems`). Moving these three functions there would centralize the dynamic-dispatch pattern and prevent future divergence if one package adds a new `KindRef` case without updating the other.

## Host function allocation per emit call

Every emit function in the `random` package calls its host factory on each invocation:

```go
func emitRandom(e module.Emitter, args []ast.Expr) {
    e.CallHost(randomHost()) // new allocation each time
}
```

This contrasts with the `math` package where `unaryFloatHost` is called once at `New()` time and the result is passed into `emitUnaryFloat` as a parameter. The `random` functions that call a factory each time (`emitRandom`, `emitRandint`, etc.) could follow the same pattern. Non-blocking — the existing pattern works correctly and the allocation cost is negligible for typical use.

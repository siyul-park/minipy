# Five stdlib native modules with ConstantSymbol infrastructure

This change adds five Python standard library modules to minipy (math, string, functools, random, sys) and the infrastructure to support them: a `ConstantSymbol` interface for non-callable module attributes, a `NativeConstant` type, a `ConstGet` Emitter method for string constant emission, and checker/lowerer paths for resolving constant symbols via both `import X; X.attr` and `from X import attr`. Each module is a standalone package following the existing `operator`/`typing` pattern, the compiler changes are minimal (two new maps, four new if-branches), and all five modules pass integration tests that verify real runtime output.

Watch for: Dynamic-typed arguments to math/random functions emit host calls with statically-typed VM parameters but no promotion when the checker returns `Any` — a confirmed gap that would cause VM type mismatches at runtime (confirmed). The `random` module uses package-level global mutable state with a mutex, making test isolation fragile and concurrent program behavior dependent on execution order (confirmed). `intBinarySymbol` factory in `math.go` conflates two unrelated signatures behind a name switch, violating coding-patterns §3.1 abstraction level (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The ConstantSymbol mechanism extends the Symbol contract with proper checker/lowerer symmetry: both `fieldType` and `nameType` detect ConstantSymbol, store it in maps, and the lowerer dispatches to `native.Emit(c, nil)` in both corresponding paths. The new `ConstGet(vmtypes.Value)` Emitter method fills a real gap — strings require constant-pool allocation which `Emit(F64_CONST, bits)` cannot express.

The `functools.reduce` uses inline-emitted bytecode loops mirroring the existing `map`/`filter` pattern, with `CheckWithHint` for lambda type inference. The empty-list error case uses a host function that unconditionally errors (workaround for no "throw exception" instruction).

The `random` module introduces package-level mutable state (`rng` + `rngMu`) — the only module with side effects beyond pure computation. The `module.Runtime` interface exists to bind per-program resources, but random bypasses it, creating an implicit process-global coupling.

The checker returns `types.Any` for dynamic inputs across math/random, but emit functions only insert int-to-float promotion when `e.Type(arg) == types.Int`. When the type is `Any`, no promotion occurs, yet host functions expect `TypeF64`. This is a confirmed gap for dynamic-typed programs.

<details>
<summary>Issues (5)</summary>

1. **Dynamic-typed math/random emit gap** — When the checker returns `types.Any` for a math/random function argument, the emitter skips int-to-float promotion but the host function expects `vmtypes.TypeF64`. Add a dynamic dispatch path (promote if int at runtime, pass through if float) or reject dynamic inputs at check time for functions requiring float.
2. **intBinarySymbol name/abstraction mismatch** — `intBinarySymbol` handles both 2-arg gcd and 1-arg factorial via an internal name switch. Split into two direct `NewSymbol` calls or rename the factory to reflect its actual behavior.
3. **Global RNG state in random module** — Package-level `rng` with a mutex makes test execution order affect results and prevents isolation between concurrent minipy programs in the same process. Consider binding the RNG source to the module runtime (like `Out()` for print) or document that `seed()` is process-global.
4. **Host function re-allocation per emit** — Functions like `gcdHost()`, `factorialHost()`, `randomHost()` etc. allocate a new `*interp.HostFunction` each time they are called by the emitter. While this matches existing patterns, it means repeated compilation of the same source allocates redundant identical objects. A package-level `var` or sync.Once would eliminate this.
5. **math.ceil/floor return float, not int** — CPython's `math.ceil(2.3)` returns `3` (int), not `3.0` (float). The current implementation returns `types.Float` for ceil/floor, which is a behavioral deviation from Python 3. Document this as an explicit restriction or implement int return.

## Dynamic-typed emit gap in math and random

The checker correctly identifies dynamic inputs and returns `types.Any`:

```go
func checkUnaryFloat(name string) module.CheckFunc {
    return func(c module.Checker, args []ast.Expr, pos token.Pos) types.Type {
        ...
        t := c.Check(args[0])
        if types.IsDynamic(t) {
            return types.Any
        }
        ...
    }
}
```

But the corresponding emitter only promotes if the compile-time type is exactly `types.Int`:

```go
func emitUnaryFloat(host *interp.HostFunction) module.EmitFunc {
    return func(e module.Emitter, args []ast.Expr) {
        e.Expr(args[0])
        if types.Equal(e.Type(args[0]), types.Int) {
            e.Emit(instr.I64_TO_F64_S)
        }
        e.CallHost(host) // host expects TypeF64
    }
}
```

When `e.Type(args[0])` is `types.Any`, the promotion is skipped. If the runtime value is an integer (i64 on the stack), the host function receives an i64 where it expects f64, which will either misinterpret the bits or trap depending on the VM's call convention. The same pattern affects `emitBinaryFloat`, `emitPredicate`, and `emitUniform` in the random module.

The fix is to either: (a) emit a dynamic type-check and conditional promotion at the emit site, or (b) reject `Any`-typed arguments with a diagnostic rather than returning `types.Any`. Option (b) is simpler and aligns with the stated preference for static types.

## intBinarySymbol factory violates single-abstraction-level

```go
func intBinarySymbol(name string, hostFn func() *interp.HostFunction) *module.NativeSymbol {
    switch name {
    case "factorial":
        return module.NewSymbol(name, checkFactorial, emitFactorial(hostFn), nil)
    default:
        return module.NewSymbol(name, checkGCD, emitGCD(hostFn), nil)
    }
}
```

This function is named "Binary" but handles the unary `factorial`, uses a string switch rather than letting the caller specify the check/emit pair, and hides which check function is used from the caller in `New()`. The coding standard (§3.1) requires each function to hold one abstraction level. This should be two direct `NewSymbol` calls at the `New()` site, just as `unaryFloat` and `binaryFloat` are separate factories for their respective arities.

## random module global state and test isolation

```go
var (
    rng   *rand.Rand
    rngMu sync.Mutex
)

func init() {
    rng = rand.New(rand.NewPCG(0, 0))
}
```

The `module.Runtime` interface exists precisely to bind per-program resources (currently just `Out() io.Writer`). If minipy ever supports concurrent program execution within one process (documented as a future possibility in coding-patterns §10), this global would need to become per-program state. The current tests handle this by always calling `seed(42)` before assertions, but two tests running concurrently would interfere.

## Untested runtime error paths

The following runtime error paths have host functions that return errors but no integration tests exercising them:
- `reduce()` with an empty list and no initial value (`ErrReduceEmpty`)
- `factorial(-1)` (negative input → `ErrFactorial`)
- `randrange(0)` / `randrange(5, 3)` (empty range → `ErrEmptyRange`)
- `choice([])` (empty sequence → `ErrEmptySequence`)

These host functions are defined and would fire at runtime, but no test verifies the error propagation through the VM trap mechanism.

## sys.exit discards the exit code

```go
func emitExit(e module.Emitter, args []ast.Expr) {
    e.Expr(args[0])
    e.Emit(instr.DROP)
    e.Emit(instr.UNREACHABLE)
}
```

The exit code is evaluated for side effects but discarded. CPython's `sys.exit()` raises `SystemExit` which can be caught; minipy's is a hard VM halt with no recovery. This is a deviation worth documenting as an explicit restriction.
